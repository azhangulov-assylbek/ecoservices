# Архитектура: модульный монолит

Платформа — один Django-проект, но каждый пользовательский сервис («Проверка объекта по НДТ»,
«ESG-отчёт по стандарту P5» и следующие) — отдельное Django-приложение. Цель: сервисы можно
разрабатывать, тестировать и включать/выключать независимо, не превращая проект в переплетённый
монолит и не переходя пока (это не нужно на этапе MVP) к микросервисам.

## Слои и кто на кого может ссылаться

```
  config/            composition root: settings.INSTALLED_APPS, settings.ENABLED_SERVICES,
  (не приложение)    config/urls.py, config/service_registry.py, config/checks.py —
                     единственное место, которое знает сервисы по имени.
        │
        │ config.service_registry.service_url_map() /
        │ enabled_service_configs()  ── только через реестр, без import сервиса
        ▼
  core, catalog      витрина (главная страница), приём заявок на оборудование,
                     модель catalog.Service — карточки сервисов в каталоге
        ▲
        │ читают catalog.Service по slug (имя/описание/статус),
        │ будут читать ndt.EmissionLimit для расчётов
        │
  ndt_check          esg_p5             ...следующие сервисы-приложения
  (сервис-приложение) (сервис-приложение) apps.py: только service_slug
  apps.py, urls.py,   apps.py, urls.py,   urls.py — свой app_name/namespace
  views.py,           views.py,           views.py — берёт catalog.Service по slug
  services.py         services.py         services.py — бизнес-логика (пока заглушка)

  Сервисы НЕ импортируют друг друга (ndt_check ↮ esg_p5).

        │ читают
        ▼
  ndt                справочники НДТ — только данные (Reference, Technique,
                     EmissionLimit), без views.py/urls.py, без пользовательских страниц
```

Правила зависимостей (проверяются на глаз при код-ревью, не линтером):

1. **Сервисы не импортируют друг друга.** `ndt_check` никогда не делает `import esg_p5` и наоборот.
   Если двум сервисам понадобится общая логика — она выносится в `ndt`, `catalog` или в будущий
   общий пакет, а не в один из сервисов.
2. **`core` и `catalog` не импортируют сервисы напрямую.** Ни `core/views.py`, ни `catalog/*`
   никогда не пишут `import ndt_check` / `from esg_p5 import ...`. Всё обращение к сервисам —
   только через `config.service_registry` (`enabled_service_configs()`, `service_url_map()`),
   которая под капотом использует рантайм-реестр приложений Django (`django.apps.apps`), а не
   прямой импорт.
3. **Сервисы могут использовать `ndt` и `catalog` как общий фундамент.** Это разрешённое
   направление зависимости (сверху вниз на схеме): например, `ndt_check.views` читает
   `catalog.models.Service`, чтобы взять название/описание/статус для своей стартовой страницы,
   а будущая бизнес-логика в `ndt_check.services` будет использовать `ndt.EmissionLimit`.
4. **`config/` — единственный слой, знающий сервисы по имени.** Помимо `settings.INSTALLED_APPS`
   и `settings.ENABLED_SERVICES`, только `config/urls.py` и `config/service_registry.py`
   обращаются к сервисным приложениям по строковому имени (`django_apps.get_app_config(label)`).

## Как устроен сервис-приложение

Минимальный набор файлов (см. `ndt_check/`, `esg_p5/` как образец):

- `apps.py` — `AppConfig` хранит **только** `service_slug` (например, `"ndt-check"`). Название,
  описание и статус («Бета» / «В разработке» / «Планируется») в `AppConfig` не дублируются — их
  единственный источник правды — `catalog.Service` с тем же `slug`.
- `urls.py` — свой `app_name` (обычно совпадает с `AppConfig.name`, например `"ndt_check"`;
  название модуля на Python не может содержать дефис, поэтому у `app_name`/namespace —
  подчёркивание, а у публичного `service_slug` и URL — дефис, как в `catalog.Service.slug`).
- `views.py` — берёт `catalog.Service` по `service_slug` (`get_object_or_404`) и рендерит
  страницу; бизнес-логику сюда не кладём.
- `services.py` — бизнес-логика сервиса. Пока — заглушка с описанием, что появится позже
  (детерминированное сравнение с НДТ, сборка ESG-отчёта и т.д.).
- `templates/<app_label>/` — свои шаблоны, наследуются от корневого `templates/base.html`,
  используют токены и классы `static/css/main.css` (без новых стилей ради одной страницы).
- `tests.py` — минимум: страница отдаёт 200, использует нужный шаблон, показывает данные из
  `catalog.Service`, смонтирована по правильному URL.

## Реестр сервисов и подключение маршрутов

- `catalog.Service.slug` — источник правды для карточки сервиса на главной (имя, описание,
  статус, группа, задачи). Значения `slug` в сеиде (`ndt-check`, `esg-p5`, ...) специально
  совпадают с `AppConfig.service_slug` соответствующих приложений — так каталог и код связаны
  по одному ключу, без ссылки на модель приложения.
- `settings.ENABLED_SERVICES` (список app label, по умолчанию читается из переменной окружения
  `ENABLED_SERVICES`, см. `.env.example`) решает, какие из установленных сервисов-приложений
  подключены: видны по URL `/services/<service_slug>/` и на главной ведут на «Открыть», а не на
  «Сообщить о запуске». **Статус сервиса в базе (`Service.status`) не влияет на то, есть ли
  рабочая ссылка — только на подпись бейджа.** Так можно держать в каталоге сервис со статусом
  «Бета», но временно отключить его для пользователей (например, на время техработ), не трогая
  данные каталога.
- `config/urls.py` при импорте вызывает `config.service_registry.enabled_service_configs()` и
  монтирует `include(f"{app_label}.urls")` под `path("services/<service_slug>/", ...)` для
  каждого включённого сервиса, с `namespace=app_label`.
- ⚠️ **`urlpatterns` строятся один раз при импорте `config/urls.py`** (то есть при старте
  процесса). Изменение `ENABLED_SERVICES` в `.env` требует перезапуска приложения — это обычное
  ограничение Django, не баг. Для тестов, которым нужно реально проверить переключение маршрутов,
  есть `config/url_reload.py` (`enabled_services(*labels)` — временно переопределяет настройку и
  форсирует пересборку `config.urls`; используется только в тестах).
- `config/checks.py` регистрирует системную проверку (`python manage.py check`,
  автоматически перед тестами и `runserver`): каждый элемент `ENABLED_SERVICES` должен быть
  установленным приложением (`config.E001`, если приложения нет) с заданным `service_slug`
  (`config.E002`, если приложение есть, но не является сервисом). Проверка регистрируется в
  `core.apps.CoreConfig.ready()`, так как `core` всегда установлен.

## Запланированные приложения (пока не создаются)

- **`accounts`** — аутентификация и личный кабинет пользователя/компании: вход, роли
  (эколог предприятия, консультант), профиль объекта. Сервисы будут ссылаться на модель
  пользователя `accounts`, а не наоборот — так же, как сейчас на `catalog`.
- **`reports`** — сборка итоговых документов (предварительная оценка по НДТ, ESG-отчёт P5) из
  данных, которые произвели сервисы: общий слой генерации PDF/DOCX, шаблоны отчётов,
  дисклеймер «предварительная оценка, не заменяет государственную экологическую экспертизу».
  Сервисы кладут результат расчёта в общий формат, `reports` его оформляет — сервисы не должны
  импортировать друг друга ради обмена данными для отчёта.
- **`ai`** — общий модуль объяснений и ответов на вопросы через внешние языковые модели
  (Claude, Gemini и др., со сменой модели одной настройкой — см. CLAUDE.md). Сравнение показателей
  с НДТ остаётся детерминированным кодом в `ndt_check`/`ndt`; `ai` только объясняет результат и
  подбирает техники со ссылкой на источник. Сервисы обращаются к `ai` как к общему сервису
  (сверху вниз на схеме), `ai` не хранит специфичную для конкретного сервиса логику.

Ни одно из этих приложений не должно превращаться в место, куда сервисы импортируют друг друга
«в обход» правила 1 — они читают из `accounts`/`ndt`/`catalog`/`ai` и пишут в `reports`, но
не видят внутренности соседних сервисов.
